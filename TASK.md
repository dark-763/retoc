# Контекст задачи

Форк retoc с девятью правками для пересборки контейнеров IoStore UE 4.26.
Рабочая ветка ue426-repack - не трогать. Экспериментировать в bundle-rule.
Ветка pack-raw-compression - для открытого PR, не трогать.

## Задача

Правка 7 (разбивка бандлов) - костыль: разбивка читается из JSON, снятого
с оригинального контейнера, через RETOC_BUNDLE_LAYOUT. Научить retoc
вычислять её самому.

## Что уже выяснено (проверено на 1243 пакетах, 0 расхождений)

Число бандлов = максимальный целевой бандл во внешних дугах графа + 1.

Регион графа (graph_off, graph_size):
  uint32 число импортируемых пакетов
    на пакет: uint64 FPackageId, uint32 число дуг, пары (uint32 from, uint32 to)
Поле to - номер принимающего бандла. to==1 бывает тогда и только тогда,
когда бандлов больше одного (557 однобандловых - ни разу).

retoc УЖЕ строит эти дуги верно: у пересобранного пакета граф совпадает
с оригиналом, включая целевой индекс 1. Данные есть, не используются.

Бандлы содержат команды (экспорт, Create|Serialize), а не экспорты:
сумма записей = export_count * 2.

Осталось распределение команд. На 1215 пакетах: у 1125 ровно один экспорт
имеет Create в бандле 0 и Serialize в бандле 1 - родитель сериализуется
после своих детей. У 394 из 487 проверенных такой экспорт имеет потомков
(другие экспорты ссылаются на него как outer).

## Статус (ветка bundle-rule)

`compute_bundle_layout()` в zen_asset_conversion.rs вычисляет разбивку из
`export_load_order` (последовательность Create/Serialize, которую retoc и
так строит верно - сверено побайтово с оригиналом на всех 1243 пакетах
через `to-legacy` -> `to-zen` без JSON).

Правило: разрез сразу после Serialize, если следующая по порядку команда -
это **Create** экспорта с МЕНЬШИМ индексом ("инверсия" - кукер отложил
создание чего-то раньше стоящего в файле до готовности чего-то более
позднего, признак настоящей перекрёстной зависимости между ветками дерева).

RETOC_BUNDLE_LAYOUT оставлен как необязательное переопределение поверх
вычисленного правила (`json_bundle_layout_override`): если переменная не
задана - работаем полностью на расчёте; если задана и в JSON есть запись
для пакета - берём её вместо расчёта. Так старый эталонный JSON остаётся
рабочим резервным путём для пакетов, на которых расчёт ошибается.

**Важно, была найдена и исправлена ошибка до коммита.** Первая версия
правила допускала разрез и когда следующая команда - Serialize (не только
Create) с меньшим индексом; это давало 1208/1243 (97.2%) точных совпадений
на ИЗВЕСТНОМ множестве из 1243 многобандловых пакетов, но при сборке ВСЕГО
проекта (17095 пакетов, `to-legacy` -> `to-zen` без JSON на всём
`D:\GameLoc-new\original_backup`, не на подмножестве) обнаружила 131 ложное
срабатывание на пакетах, у которых в оригинале ровно один бандл (например
BP_TunnelBend_90: было 1, стало 2) - тест на одном лишь известном
множестве 1243 пакетов не мог поймать такую регрессию, потому что оно по
построению (dump_bundle_layout.py) содержит только уже-многобандловые
пакеты. Правило сужено до "только Create" - на всём проекте (17095 пакетов)
это даёт **0 ложных срабатываний** ценой меньшей полноты: 1134/1243 (91.3%)
точных совпадений вместо 1208, разница полностью в сторону "бандлов
меньше, чем в оригинале", никогда не больше.

## Дедупликация дуг (правка №8, вторая итерация)

### Что означает поле `from`

Гипотеза из постановки задачи (0=Create, 1=Serialize, 2=пакет готов целиком)
**отвергнута**. Прямая проверка по данным оригинала (все 17095 пакетов,
103073 дуги, читал `D:\GameLoc-new\raw_out_0916\chunks\<cid>` напрямую с
диска - `unpack-raw` уже распаковал оригинал туда, не нужно гонять `retoc
get` по одному чанку): для КАЖДОЙ дуги проверил `from < export_bundle_count
пакета-источника` (просмотрел исходный пакет по `pkg_id` из дуги) - **выполняется
всегда, без единого исключения** (103071 из 103071 проверенных; 2 дуги
сослались на пакет вне манифеста, видимо движковый). Будь `from` типом
команды, а не индексом бандла, он бы никак не был ограничен числом бандлов
СОВЕРШЕННО ДРУГОГО, произвольного пакета - совпадение было бы случайным.
Значит **`from` - это в точности то, что и предполагает текущий код
(`from_export_bundle_index`): индекс бандла экспортов В ПАКЕТЕ-ИСТОЧНИКЕ**,
из которого что-то нужно этому пакету раньше, чем бандл `to` в НЁМ САМОМ
станет готов к использованию.

Распределение `from`: 0 (101295), 2 (1478), 1 (298), 0xFFFFFFFF=-1 (2,
служебное значение "источник не найден", см. `fixup_legacy_external_arcs`).
Наблюдение из постановки "2 только в паре с to==1" почти верно, но не
абсолютно: пар (2,1) - 1444, но есть и (2,2) - 34 штуки. Не противоречит
интерпретации "from - это индекс бандла": `from=2` просто требует, чтобы у
ПАКЕТА-ИСТОЧНИКА было хотя бы 3 бандла, что редко (отсюда и редкость from=2
вообще), а to может быть любым бандлом ЭТОГО пакета, куда бы ни попала
конкретная зависимость.

### Настоящая причина 0 из 1134

Правка №8 убрала `from_export_bundle_index` из ключа дедупликации ПОТОМУ
ЧТО на момент создания дуги это ещё не настоящий индекс бандла, а
одноразовый номер-заглушка (`legacy_external_arc_counter`, инкрементируется
на КАЖДЫЙ вызов) для последующей подстановки в `fixup_legacy_external_arcs`
- дедуп по нему был бессмысленным (каждая дуга уникальна по построению) и
только размножал дуги. Но ключ без `from` тоже неверен: оригинал хранит и
`(id, from=0, to=1)`, и `(id, from=2, to=1)` - то есть `from` ПОСЛЕ
разрешения значим и дедуп обязан его учитывать.

Ловушка в том, что "правильный from" вычисляется ТОЛЬКО в отдельном
глобальном проходе `fixup_legacy_external_arcs`, который выполняется ПОСЛЕ
того, как ВСЕ пакеты уже сериализованы в байты (см. вызов в
`retoc_cli/src/main.rs` ~927: сначала все `build_zen_asset` в `converted_lookup`,
потом цикл `fixup_legacy_external_arcs` по каждому, потом запись на диск) -
именно потому, что зависимость может указывать на пакет, который ещё не
обработан (`rayon`, порядок не гарантирован). До этого прохода МЫ НЕ ЗНАЕМ,
разрешатся ли два разных импорта одного и того же внешнего пакета в один и
тот же бандл или в разные - поэтому дедуп в момент создания дуги (что
правка №8, что первая попытка её поправить в этой сессии - ключ по
`package_object_import`) в принципе не может быть точным: первый вариант
схлопывает то, что не должно схлопываться (испытано и отклонено выше),
второй наоборот пропускает дубли (проверено: пакет `12902175980756718967`
получал 17 одинаковых `(0, 1)` дуг вместо одной - 17 разных импортов ИЗ
этого пакета оказались все в его бандле 0).

**Правильное место для дедупликации - ПОСЛЕ `fixup_legacy_external_arcs`**,
когда `from` уже настоящий. К этому моменту пакет уже полностью
сериализован в байты (`self.package_buffer`), а не хранится как структура -
переделывать архитектуру (откладывать сериализацию до глобальной фиксации)
не стал: это большая, рискованная переделка ради узкой задачи. Вместо этого
`dedup_legacy_dependency_arcs()` в `zen_asset_conversion.rs` патчит уже
сериализованные байты НАПРЯМУЮ:

1. Область графа - всегда последняя часть заголовка для
   `container_header_version <= Initial` (проверено по `FZenPackageHeader::serialize`
   - `header_size` фиксируется сразу после записи графа), поэтому её можно
   сжать, просто вырезав лишние байты (`Vec::splice`) - ничего до неё или
   после нужного пересчёта смещений не требует (данные экспортов идут
   отдельным куском сразу после и просто сдвигаются как единый блок).
2. `graph_data_size` лежит по фиксированному смещению 56 байт от начала
   `FZenPackageSummary` для `<= Initial` (проверено побайтово: 8 байт name +
   8 байт source_name + 4 package_flags + 4 cooked_header_size + 4×4 полей
   name map + import_map_offset(4) + export_map_offset(4) +
   export_bundle_entries_offset(4) + graph_data_offset(4) = 56) - патчится
   тем же способом, каким код уже патчит отдельные `from` в этом же файле.
3. `store_entry.export_bundles_size` (= header_size + сумма размеров
   экспортов) уменьшается на столько же байт, на сколько сжался граф.
4. Дедуп идёт ПОБЛОЧНО (в пределах одного импортируемого пакета), парой
   `(from, to)`, с сохранением порядка первого вхождения.

### Проверенные и отвергнутые гипотезы (не тратить время повторно)

- Настоящий флаг EObjectFlags::Public у экспорта - не коррелирует с границей
  (только 49 из 1271 реальных границ на экспорте с этим флагом).
- Любой экспорт с детьми (Outer) как триггер границы - даёт тысячи ложных
  срабатываний на больших/глубоких пакетах.
- "Корневой" (Outer==NULL) экспорт с детьми - предсказывает не тот узел на
  глубоко вложенных пакетах (граница может быть на внуке корня, не на корне).
- Цель preload-зависимости SerializeBeforeCreate (данные для этого УЖЕ
  корректно вычисляются и используются для порядка, см. export_dependencies)
  - слишком широкий сигнал, совпадает почти с каждым Serialize в пакете.
  Настоящие межпакетные циклы (прямой 2-цикл через imported_packages) тоже

- Обнуление глубины вложенности (открытые Create без Serialize) - см. выше.
- "Чистый остров" (span Create..Serialize контейнера содержит только его же
  потомков, без посторонних) - даёт тысячи ложных срабатываний, т.к. в
  глубоких деревьях таких чистых островков много на разных уровнях, а
  реальная граница - только на одном конкретном.

## imported_packages (правка №10, ветка imported-order)

Нумерация: компрессия в pack-raw уже занимает №9 в README-ue426.md/
PATCHES-en.md (была реализована раньше, в ветке ue426-repack) - эта правка
десятая по счёту, не девятая (в первом коммите на этой ветке ошибочно
назвал её "fix 9", в документации и далее в TASK.md - "fix 10").

### Задача

`StoreEntry.imported_packages` не совпадал на 3625 из 17095 пакетов. В
TASK.md/PATCHES-en.md (fix 5) это числилось как "отличается только порядок,
кукер не сортирует этот список" - но это никогда не проверялось предметно.

### Состав vs порядок

Из 3625 расхождений у **3618 состав идентичен** (тот же набор ID, другой
порядок), у **7 состав расходится** - и это ВСЕГДА одна и та же картина:
у оригинала на один элемент больше, у нас его вообще нет.

Проверено на всех 17095 пакетах (`to-zen` без RETOC_BUNDLE_LAYOUT из
`D:\GameLoc-new\fin_0916`, сравнение с `D:\GameLoc-new\raw_out_0916`).
7 "лишних в оригинале" ID (`10302301616881458927` встречается в 6 пакетах,
`7979332950583999727` в одном - PERSISTENT.umap) не соответствуют НИ ОДНОМУ
cid ни в нашем манифесте, ни в оригинальном - то есть это ссылка на пакет, у
которого попросту нет собственного чанка в этом контейнере (внешняя/чужая
зависимость, а не движковый ассет и не что-то из известных пробелов).

Причина найдена в `resolve_package_import_internal_legacy` (`asset_conversion.rs`,
направление zen -> legacy): для `container_header_version <= Initial`
разрешение импорта идёт НЕ по индексу в `imported_packages`, а поиском - код
перебирает ВСЕ пакеты из `package_header.imported_packages` оригинала и ищет
среди их экспортов совпадение по `legacy_global_import_index()`. Значит
`imported_packages` в оригинале - самостоятельный список, не обязанный 1:1
соответствовать `import_map` пакета: кукер мог занести туда пакет, на который
есть зависимость, но НИ ОДИН элемент `import_map` на него не ссылается
напрямую (что-то вроде "мягкой"/учётной зависимости без прямого импорта
объекта). У таких 7 пакетов `to-legacy` не создаёт для этой зависимости
никакой записи в таблице импортов легаси-файла вообще - ни обычной, ни
"голого пакета" - потому что реконструировать её неоткуда: в `import_map`
исходного zen-пакета для неё просто нет соответствующей записи. Проверено
экспериментально: добавление в `to-zen` кода, который дополнительно
регистрирует "голые" (без вложенного объекта) пакетные импорты в
`imported_packages`, не изменило результат ни на одном из 7 пакетов - значит
потеря происходит раньше, при `to-legacy`, не при `to-zen` (правка отменена,
в текущем коде её нет). Чинить пришлось бы синтезом лишней записи импорта
прямо в `to-legacy` по данным `imported_packages` контейнера-источника - это
трогает другой файл и другое направление конвертации ради 7 пакетов из
17095 (0.04%), решено не делать в рамках этой задачи.

### Порядок: перебор гипотез

Проверено на оригинальном манифесте (`D:\GameLoc-new\raw_out_0916`), без
пересборки, по всем 7337 пакетам с >1 импортом:

| гипотеза | точных совпадений |
|---|---|
| по `FPackageId` (возр./убыв.) | 18.0% / 10.0% |
| по глобальному `load_order` импортируемого пакета (возр./убыв.) | 7.9% / 21.0% |
| по длине пути | 22.2% |
| по basename (без пути) | 36.8% |
| **по имени пакета (`/Game/...`), регистронезависимо, по алфавиту** | **98.6%** |

Алфавитный порядок по имени пакета (не по диречному пути - тот дал 98.61%,
имя `/Game/...` чуть точнее, 98.66%, вероятно потому что это тот же формат
строки, который использует сам кукер) на порядок точнее всех остальных
гипотез. Реализовано в `zen_asset_conversion.rs`,
`build_zen_dependency_bundles_legacy`: `imported_package_names` теперь
заполняется и для legacy (<= Initial) пути импорта (раньше заполнялся
только для UE5.0+), после чего `imported_packages` /
`imported_package_names` / `external_package_dependencies` переупорядочиваются
одним стабильным `sort_by` по `to_lowercase()` этого имени. Безопасно: обе
арки (external/legacy dependency arcs) адресуются по ID пакета или по паре
(исходный пакет, индекс импорта), не по позиции в этих трёх массивах, а
блоки графа сортируются отдельно по `FPackageId` уже на сериализации
(`zen.rs`, `non_empty_dependencies.sort_by_key`) - переупорядочивание не
могло задеть ни то, ни другое, что и подтверждено измерением (см. ниже).

Проверенная и отвергнутая гипотеза: "порядок первого обращения при обходе
экспортов 0..N, Create-зависимости потом Serialize-зависимости" (тот же
проход, что строит `legacy_dependency_arcs` в `build_zen_dependency_bundles_legacy`)
- дала РЕЗУЛЬТАТ ХУЖЕ исходного (5936 расхождений вместо 3625) и была
отброшена, а не просто не помогла.

Рабочая (до сегодняшнего дня) резервная сборка датирована 16 сентября -

  `IoStoreWriter::new`, `toc.container_id = FIoContainerId::from_name(&name)`

- Написал СВОЙ, независимый Python-парсер формата `FIoContainerHeader`/

  сверил все смещения и размеры полей против `container_header.rs` вручную,
  байт в байт) и напрямую разобрал СЫРОЙ чанк заголовка контейнера
  (`retoc.exe info` -> `container_id` -> байт-реверс -> имя файла чанка в
  `chunks/`) из результата теста с пустым списком. **Мой парсер показал
  `array_num=0`** (то есть на диске корректно лежит пустой список, как мы и
  просили) - при этом `export_count`, `export_bundle_count`, `load_order` из
  моего разбора ТОЧНО совпали с тем, что вернул `retoc unpack-raw` для этого
  же пакета (подтверждает, что я разобрал правильную запись, не промахнулся
  мимо), а вот `imported_packages` и `export_bundles_size` - НЕТ.

Итого на тот момент: на диске (по моему независимому разбору) лежит именно
то, что мы просили записать (пусто). Но `retoc unpack-raw`, читая ЭТОТ ЖЕ
файл, почему-то возвращает 8-элементный оригинальный список.

Контрольный опыт для масштаба: пропустил `raw_pristine` через `pack-raw`
БЕЗ каких-либо изменений (то есть на входе уже "правильные" по построению
данные) - результат идеально совпал с исходным на ВСЕХ 17095 пакетах, 0
расхождений. Значит бага нет "всегда" - он проявляется только когда
записываемое значение ОТЛИЧАЕТСЯ от того, что каким-то образом "ожидается".

**Найдено окончательно после ещё одного раунда диагностики** (пользователь
попросил проверить именно гипотезу про смещения в `FFilePackageStoreEntry`
- она отвела в сторону, но заодно вскрыла настоящую причину). Вместо
доверия своему Python-парсеру поставил `eprintln!` прямо внутри РЕАЛЬНОГО
кода `StoreEntries::deserialize` и `StoreEntries::serialize` в
`container_header.rs`, с проверкой по package_id. Оказалось:

- **На записи** наш целевой пакет (`17322170839476695797`) сидит в
  BTreeMap-порядке на позиции **16074**, и `imported_packages` там - именно
  то, что мы просили (`[]` в тесте с пустым списком). Мой Python-парсер был
  прав насчёт ЗНАЧЕНИЯ, но использовал НЕВЕРНЫЙ ИНДЕКС для его поиска.
- **На чтении** ТОТ ЖЕ пакет обнаруживается на позиции **1090**, с
  `array_num=8` (оригинальные, чужие данные).

Один и тот же package_id на РАЗНЫХ позициях при записи и при чтении одного
и того же файла означает одно: **это два РАЗНЫХ чанка заголовка
контейнера**, не один и тот же, прочитанный дважды по-разному.

Причина: `unpack-raw` дампит ВСЕ чанки контейнера, включая чанк САМОГО
ЗАГОЛОВКА (тип `ContainerHeader`, у него нет пути, поэтому он никогда не
попадает под замену `patch_smart.py`, но физически лежит файлом в
`chunks/`). `action_pack_raw` (`retoc_cli/src/main.rs`) копирует ЛЮБОЙ
"сырой" чанк из входной папки через `write_chunk_raw`, если он не найден в
`package_store_entries` - включая этот СТАРЫЙ (от оригинала) заголовок.
Затем `IoStoreWriter::finalize()` СТРОИТ И ЗАПИСЫВАЕТ СВОЙ, ПРАВИЛЬНЫЙ,
свежий заголовок (из `manifest.package_store_entries`) - под ТЕМ ЖЕ типом
чанка, в САМОМ КОНЦЕ файла. В итоге в одном контейнере оказываются ДВА
чанка заголовка. При чтении `IoStoreContainer::open()` находит "тот самый"
заголовок через `container.chunks().find(|info| info.id().get_chunk_type()
== EIoChunkType::ContainerHeader)` - **первое совпадение по TYPE**, без
проверки конкретного id. Поскольку старая (скопированная) копия попадает в
TOC РАНЬШЕ свежепостроенной (копирование - в основном цикле, `finalize()` -
после него), `.find()` всегда находит СТАРУЮ.

Подтверждено экспериментально: вручную удалил файл старого чанка заголовка
(`89977b982804cce80000000a` в моём тесте, определяется по суффиксу типа
`...0000000a` = `ContainerHeader` для старого/до-UE5 кодирования, см.
`EIoChunkType::value(false)` в `lib.rs`) из входной папки перед `pack-raw` -
результат СРАЗУ стал правильным (`array_num=0`, пустой список, как и
просили), без единой другой правки.

Это ОБЪЯСНЯЕТ и находку про "~85 пакетов" (правка №10): для подавляющего
большинства пакетов НАША вычисленная `imported_packages` (по имени,
сортировка) СОВПАДАЕТ с тем, что уже лежало в СТАРОМ (оригинальном)
заголовке - поэтому чтение "не того" заголовка не давало видимой разницы.
Расхождение проявлялось только там, где наши данные ГЕНУИННО отличались от
оригинала (сортировка отличалась порядком у некоторых версий кода, или
состав отличался у известных 8 композиционных случаев) - именно эти ~85
пакетов "маскировали" баг под "наша сортировка не идеальна", хотя на самом
деле дело было не в сортировке вообще, а в том, что читался чужой
заголовок.

**Фикс** (`retoc_cli/src/main.rs`, `action_pack_raw`, коммит "Fix pack-raw
duplicating the container header chunk (fix 12)"): пропускать во входном
цикле копирования ЛЮБОЙ чанк с типом `ContainerHeader` - `finalize()` и так
всегда строит и пишет правильный, копировать старый незачем никогда.

**Проверено на всём проекте** (17095 пакетов, тот же реальный пайплайн:
`to-zen` без JSON -> `unpack-raw` свежего оригинала -> `patch_smart.py` ->
`pack-raw` (фикс) -> `unpack-raw`): **0 расхождений** `imported_packages`
(ни порядка, ни состава) на ВСЕХ 17095 пакетах, и 0 расхождений во всех
остальных полях StoreEntry. Число чанков в результате - 19779, как и
должно быть (было 19780 - с лишним, старым заголовком).

**Это не апстримный баг** - `action_pack_raw` целиком в нашем форке
(`retoc_cli/src/main.rs`), апстримный `container_header.rs` действительно
ни при чём, как и предполагалось раньше, просто по другой причине: не
потому что баг где-то за пределами прочитанного кода, а потому что
искать нужно было не в `container_header.rs` вообще. PR апстриму не нужен -
всё внутри этого форка.

## "0 дуг с индексом >= bundle_count" - буквальная гипотеза не подтверждается, и не может

Перепроверил не только на 10 из патч-листа (см. выше), а на ВСЕХ 109
пакетах с неверным `export_bundle_count` (против `raw_pristine`): сколько
дуг во всём проекте (17095 пакетов) ссылаются на индекс бандла
`from_export_bundle_index >= export_bundle_count` пакета-источника, если
источник - один из 109. Результат: **0 из 0**, как и на 10 из патч-листа.

Это не совпадение и не ограничение выборки - это математическая гарантия
текущего кода. `fixup_legacy_external_arcs` резолвит `from` не копированием
сырого индекса, а поиском по `legacy_export_bundle_mapping_data` (пара
export_index+command_type -> в какой бандл ЭТОТ пакет реально его положил).
Результат поиска ПО ПОСТРОЕНИЮ всегда < `export_bundle_count` этого же
пакета, потому что `legacy_export_bundle_mapping_data` заполняется в ТОМ
ЖЕ проходе, что и сам подсчёт бандлов. Значит "дуга ссылается на
несуществующий бандл" в смысле буквального `from >= bundle_count` в
текущей реализации ретока произойти не может НИКОГДА, независимо от того,
правильно мы посчитали бандлы или нет - это не сигнал.

Так что если механизм зависания - именно через дуги/барьеры, то не через
СЫРОЙ невалидный индекс, а через что-то другое (пропавшие дуги - см. более
раннюю находку про `AC_Interact_Tracer`, где дуга с `from=1` у пакета,
получившего у нас 1 бандл вместо 2, просто НЕ СОЗДАЁТСЯ, а не создаётся с
плохим индексом; либо через сам факт неверного `export_bundle_count`,
влияющий на что-то за пределами смоделированного ретоком). Опыт (раздел
выше) доказывает СВЯЗЬ с 109 пакетами железно; какой именно из этих под-
механизмов виноват - осталось невыясненным, и без исходников 4.26
(`AsyncLoading` для Initial-формата, которого у нас нет даже в UE 5.0) это,
похоже, недоказуемо изнутри retoc.

## Автоматическое предупреждение о неопределённой раскладке (правка №11)

Раз буквальная проверка "индекс >= bundle_count" технически невозможна (см.
выше), реализовал другой, слабый, но ненулевой сигнал: диагностическую
проверку РАСХОЖДЕНИЯ между рабочим (узким, "только Create") и отвергнутым
широким ("любая команда с меньшим индексом") правилами разбивки. Она не
меняет саму раскладку - только решает, печатать предупреждение или нет.

Реализация в `zen_asset_conversion.rs`: `compute_bundle_layout` разделён на
общую `compute_bundle_layout_cuts(export_load_order, wide: bool)` и
`warn_if_bundle_layout_uncertain`, вызываемую в момент выбора раскладки,
только если `RETOC_BUNDLE_LAYOUT` НЕ покрывает пакет (если покрывает - уже
есть эталон, предупреждать не о чем). Предупреждение печатается через
существующий `warning!(builder.log, ...)`.

**Измеренная точность** (весь проект, 17095 пакетов, без JSON): 12
предупреждений, из них **7 реально входят в известные 109** (включая
`WBP_Inventory` - один из 10, что реально патчатся), 5 - ложные
срабатывания (узкое правило там как раз право, широкое ошиблось бы).
**Полнота слабая: ловит только 7 из 109 (~6%)** - оба известных класса
остатка (одноэкспортные native-типы; Blueprint-контейнеры без инверсии
индекса вообще) не имеют условия "следующий индекс меньше" ни для узкого,
ни для широкого правила, поэтому в принципе не могут быть пойманы этим
способом. Отсутствие предупреждения НЕ гарантирует, что раскладка верна;
наличие - надёжный повод перепроверить именно этот пакет. Задокументировано
прямо в doc-комментарии функции с этими же цифрами, чтобы будущий читатель
кода не переоценил надёжность сигнала.

Побочное наблюдение при проверке: в этом (закрытом, неинтерактивном)
окружении `warning!` ни разу не показался в выводе `to-zen` - indicatif
(прогресс-бар) скрывает вывод, когда stdout не терминал, и `println` поверх
скрытого бара, похоже, тоже проглатывается. Подтвердил, что САМА ЛОГИКА
срабатывает (временный `eprintln!` в том же месте показал те же 12 пакетов,
убран перед коммитом) - это ограничение вывода в конкретно моём тестовом
окружении, не баг предупреждения. У реального пользователя в обычном
интерактивном терминале индикатиф ведёт себя иначе - не чинил, вне рамок
задачи.

## ГЛАВНОЕ СЛЕДСТВИЕ правки №12: движок никогда не читал наш заголовок

Формулировка выше ("баг в pack-raw, из-за которого чтение брало чужой
заголовок") описывает следствие слишком узко, как дефект диагностики. На
самом деле следствие шире и меняет толкование ВСЕХ прошлых проверок.

`IoStoreContainer::open()` ищет заголовок как ПЕРВОЕ совпадение по типу
чанка. Так читает не только `retoc unpack-raw` - так читает и САМ ДВИЖОК,
из того же самого контейнера. Значит всё время, пока в контейнере лежали
два чанка заголовка, игра брала СТАРЫЙ, скопированный из оригинала.

**Следствие: `StoreEntry` никогда не доходил до движка.** Ни `load_order`,
ни `export_bundle_count`, ни `export_bundles_size`, ни `imported_packages`.
До движка доходили только ДАННЫЕ чанков пакетов (байты zen-пакетов, которые
подменяет `patch_smart.py`) - а весь слой метаданных контейнера брался из
оригинала, каким бы мы его ни посчитали.

Этим же объясняются **идеальные нули в `compare_store.py` по готовому
контейнеру**, которые раньше удивляли и списывались на "значит всё сошлось":
сравнивался оригинальный заголовок сам с собой. Это была тавтология, а не
измерение.

### Предупреждения, которые мы решили не читать

Оба серьёзных дефекта этой недели были ОБЪЯВЛЕНЫ инструментом открытым
текстом задолго до того, как их нашли, и оба были сочтены безобидными.
Это одна семья ошибок, и она стоила больше, чем сами дефекты.

**1. Лишний чанк: 19780 вместо 19779.** Наблюдался ещё 16 сентября.
Истолкован как безобидная особенность упаковки - "ну на один чанк больше,
данные же те же". На деле лишний чанк был не балластом, а АКТИВНО
ЗАТЕНЯЮЩИМ правильный. Подтверждено прямо: `retoc info` по установленной
в игру рабочей сборке (файлы 18.09 00:59) показывает ровно `chunks: 19780`.

**2. `warning: output filename collision` от cargo.** Печаталось с самого
первого дня, при каждой сборке, потому что в воркспейсе было две бинарных
цели с именем `retoc` (см. отдельный раздел ниже). Сочтено косметикой. На
деле это означало, что какой из двух РАЗНЫХ исходников попадёт в
`retoc.exe`, решает порядок сборки, и только в одном из них жил фикс №12.

Правило на будущее: предупреждение инструмента или расхождение двух
величин, которые обязаны совпадать - это ЗАЦЕПКА, которую доводят до
названной причины, а не шум. "Наверное, безобидно" - это гипотеза, и
доказательств она требует ровно столько же, сколько любая другая.
Расхождение в числе чанков/записей не косметика, пока не установлено, ЧТО
именно лишнее и КТО его читает.

### Ни одна установленная сборка фикса не содержала

Рабочая сборка, на которой основан вывод "с `RETOC_BUNDLE_LAYOUT`
запускается" - файлы от **18.09 00:59**. Коммит фикса `1568cff` сделан
**18.09 09:31**, на восемь с половиной часов позже. То есть ВСЕ три строки
таблицы опыта про зависание (`ue426-repack`, `imported-order` без JSON,
`imported-order` с JSON) собраны БЕЗ фикса №12 и все три читали
оригинальный заголовок.

### Что это означает для прошлых выводов

- **"Собрали, запустилось, работает" - свидетельство только о БАЙТАХ
  пакетов, не о нашем `StoreEntry`.** Проверенным можно считать только
  то, что наша конвертация zen-пакетов даёт данные, которые движок
  переваривает при ОРИГИНАЛЬНЫХ метаданных контейнера.
- Правки, которые живут целиком в `StoreEntry` (№10 - сортировка
  `imported_packages`; любое влияние `export_bundles_size`), НИКОГДА не
  проверялись в игре - ни в плюс, ни в минус. Их "безвредность" не
  установлена, она просто не могла проявиться.
- После фикса игра ВПЕРВЫЕ прочитает наш заголовок. Это **не улучшение
  ранее работавшего, а первый честный прогон.** Отсутствие регрессий в
  прошлом ничего не обещает: раньше этот слой данных был отключён.

### Переосмысление механизма зависания (109 пакетов)

Опыт с тремя сборками (см. таблицу выше) остаётся в силе как ФАКТ, но его
объяснение становится точнее и проще, чем "барьеры в AsyncLoading2".

Раз заголовок читался оригинальный, то `export_bundle_count` движок брал
ИЗ ОРИГИНАЛА во всех трёх сборках. А байты пакетов - наши, для 1096
подменяемых файлов. Из 109 пакетов с неверной расчётной разбивкой в
`patch_0916.txt` попадают ровно 10 (см. "Проверка 3"). Для этих 10 в
сборках без JSON возникала ПРЯМАЯ несостыковка: заголовок (из оригинала)
объявляет движку 2 бандла, а подставленные нами байты пакета содержат 1.
С JSON разбивка совпадала с оригинальной - несостыковки не было, и игра
запускалась.

Это объясняет опыт полностью, без апелляции к недоказуемой модели
барьеров, и согласуется с находкой "0 дуг с индексом >= bundle_count":
невалидного индекса в дугах и правда не было, рассогласование было между
СЛОЯМИ (заголовок против данных), а не внутри дуг.

### Следствие: вывод "RETOC_BUNDLE_LAYOUT обязателен" может быть артефактом бага

Это не мелкое уточнение механизма, а пересмотр главного практического
вывода вчерашнего дня.

До фикса №12 стороны были РАЗНОРОДНЫ по построению: заголовок всегда
оригинальный, байты пакетов - наши. При такой конструкции наша расчётная
разбивка не могла не конфликтовать с заголовком, как бы хорошо мы её ни
считали: заголовок просто НЕ ЗНАЛ о нашем расчёте. JSON "помогал" не
потому, что движку нужна оригинальная раскладка как таковая, а потому что
он делал нашу раскладку совпадающей с той, о которой заголовок и так
сообщал. То есть RETOC_BUNDLE_LAYOUT был лекарством от рассогласования
слоёв, а не от неверной раскладки.

После фикса №12 обе стороны становятся НАШИМИ и согласуются между собой
автоматически - заголовок строится из того же манифеста, что описывает
подставленные байты. Значит расчётная разбивка получает первый настоящий
шанс, а 109 пакетов могут оказаться вовсе не смертельными: они будут
отличаться от оригинала, но не будут противоречить собственному заголовку.

**Решающий опыт (порядок строгий, одна переменная за раз):**

1. Сборка С `RETOC_BUNDLE_LAYOUT` и С фиксом №12 - убедиться, что с
   правильным заголовком игра вообще работает. Это контроль: он отделяет
   "фикс сам по себе безопасен" от всего остального.
2. Только после этого - сборка БЕЗ `RETOC_BUNDLE_LAYOUT`, но С фиксом.
   Это и есть решающий опыт. Заработает - значит правка №7 полноценна,
   JSON больше не нужен, и предупреждение в README-ue426.md /
   PATCHES-en.md ("RETOC_BUNDLE_LAYOUT обязателен для шипинга", коммит
   `a15a8d7`) надо переписывать: оно описывало следствие бага, а не
   свойство формата. Не заработает - значит движку нужна именно
   ОРИГИНАЛЬНАЯ раскладка (вероятнее всего из-за дуг от ДРУГИХ пакетов,
   ссылающихся на бандл, которого у наших 109 нет), и тогда вывод
   остаётся в силе, но уже на честном основании.

До фикса различить эти две гипотезы было невозможно в принципе - любая
сборка без JSON рассогласовывала слои и потому падала независимо от того,
верна раскладка или нет. Это первый за всю историю задачи способ их
развести.

### Что требует перепроверки в первую очередь

1. `load_order` - он единственный, кто раньше доходил до движка ВЕРНЫМ
   (из оригинального заголовка) и теперь пойдёт из нашего манифеста.
   `patch_smart.py` его специально сохраняет из оригинала (строки 56-59,
   `new_entry["load_order"] = original_load_order`), а непатченные ~16
   тысяч записей приходят из `unpack-raw` оригинала как есть - по коду
   всё должно сойтись, но раз этот путь НИ РАЗУ не был задействован в
   реальной сборке, его надо измерить, а не вычитать.
2. `export_bundles_size` - расхождение на 2559 пакетах числилось как
   "ожидаемо от перевода" и никого не беспокоило, потому что до движка
   не доходило. Теперь дойдёт. Надо понять, ЧТО движок с ним делает
   (размер региона для чтения? проверка?) - раньше этот вопрос был
   безобиден, теперь нет.
3. `imported_packages` (правка №10) - впервые получит шанс повлиять на
   загрузку, в обе стороны.

### Имя выходного файла теперь значимо: `container_id`

Обнаружено при подготовке сборки №1. `IoStoreWriter::new`
(`iostore_writer.rs:29,36,49`) берёт `file_stem` выходного `.utoc` и
считает `toc.container_id = FIoContainerId::from_name(&name)`, **а затем
передаёт этот же id в `FIoContainerHeader::new(v, toc.container_id)`** -
то есть id попадает И в TOC, И внутрь чанка заголовка контейнера.

Установленная рабочая сборка имеет `container_id: ae04081d344b216e`, а
оригинал - `e8cc0428987b9789`.

Первая гипотеза была "прошлый пайплайн паковал под временным именем" -
**проверена и ОТВЕРГНУТА**: сборка №1 запакована СРАЗУ под финальным
именем `SRTE-WindowsNoEditor.utoc` и всё равно получила `ae04081d344b216e`,
то есть ровно тот же id, что у прошлой рабочей сборки. Значит имя было
финальным и раньше, а расходится не имя, а САМА ФОРМУЛА: наш
`from_name` = `lower_utf16_cityhash` (CityHash64 от utf16-le строки,
приведённой к нижнему регистру, `lib.rs:744`) для строки
`SRTE-WindowsNoEditor` даёт `ae04...`, тогда как кукер записал `e8cc...`.
Из какой строки (или каким хешем) кукер это получил - **не выяснено**,
подбор не проводился (нет готового CityHash64 в питоне под рукой, а ради
этого собирать отдельный крейт посреди опыта не стал).

Что из этого практически важно:

- id попадает и в TOC, и внутрь чанка заголовка
  (`FIoContainerHeader::new(v, toc.container_id)`, `iostore_writer.rs:49`).
- ДО фикса №12 у контейнера были одновременно TOC с `ae04...` и
  ЧИТАЕМЫЙ (старый, оригинальный) заголовок с `e8cc...` - то есть слои
  расходились и по id тоже, и игра это пережила.
- ПОСЛЕ фикса обе стороны наши и согласованы (`ae04...` и там, и там),
  но обе отличаются от оригинального `e8cc...`.
- Новой переменной относительно рабочей сборки это НЕ создаёт: в TOC
  у неё уже лежал `ae04...`. Новое только то, что теперь и заголовок
  говорит то же самое вместо `e8cc...`.

Отдельный открытый вопрос на будущее: воспроизвести формулу кукера и
выяснить, читает ли движок `container_id` заголовка. Переименование файла
задним числом id уже не меняет - он записан в байты обоих мест.

### Незакрытое отличие: флаг `Compressed` в `container_flags`

Замечено попутно, НЕ трогал (это была бы вторая переменная). Оригинал:
`container_flags: EIoContainerFlags(Compressed | Indexed)`. И установленная
рабочая сборка, и сборка №1: `EIoContainerFlags(Indexed)` - без
`Compressed`, хотя `compression_methods: [Zlib]` и блоки реально сжаты
(размер .ucas 9.6 ГБ против 18.6 ГБ несжатого). Причина в коде:
`IoStoreWriter::new` вообще никогда не выставляет `container_flags`,
оставляя значение по умолчанию из `Toc::new()`.

Для текущего опыта это НЕ переменная - флага нет одинаково и у рабочей
сборки, и у новой, так что различие между ними им не объясняется. Но как
отличие от оригинала оно до сих пор никем не разбиралось и попадает ровно
в ту категорию, из-за которой мы уже дважды обожглись. Отдельная задача:
выяснить, читает ли движок этот флаг, и если да - выставлять его при
включённом сжатии.

**Предсказание для сборки №2 (без JSON):** `export_bundle_count` разойдётся
на 10 пакетах (пересечение известных 109 с `patch_0916.txt`, см.
"Проверка 3"), плюс те же 2 Engine-submix останутся оригинальными, так как
не патчатся. Если сборка №2 работает - значит несовпадение с оригиналом по
раскладке само по себе не смертельно, смертельным было рассогласование

## Дубль бинарной цели: две `retoc.exe` из разных исходников

Найдено при разборе следствия выше. В воркспейсе **две бинарные цели с
одним именем `retoc`**:

- `retoc_cli/src/main.rs` (объявлена явно через `[[bin]] name = "retoc"`)
- `retoc/src/main.rs` (автоподхват: в пакете `retoc` есть и `lib.rs`, и
  `main.rs`, cargo делает из последнего бинарь по имени пакета)

Обе пишут в `target/release/retoc.exe`, и cargo это прямо сообщает:
`warning: output filename collision ... this may become a hard error`.
Какая победит - зависит от порядка сборки, не от нашего выбора.

`retoc/src/main.rs` - **наш собственный случайный дубль**, добавлен
коммитом `ea8d787` (1131 строка, `git log --diff-filter=A` подтверждает,
что раньше файла не было; при сплите крейтов `3cf7857` он не создавался,
апстрим его не имеет).

Содержательно файлы совпадают: `diff` даёт только разницу в отступах
(в `retoc_cli` часть блоков сдвинута) плюс **сам фикс №12, который есть
ТОЛЬКО в `retoc_cli/src/main.rs`**. То есть до 18.09 обе цели вели себя
одинаково и прошлые сборки от этого дубля не пострадали - но теперь
расхождение поведенческое: если коллизия разрешится в пользу пакета
`retoc`, фикс №12 молча исчезнет из собранного `retoc.exe`, без единой
ошибки компиляции.

Текущий `target/release/retoc.exe` (18.09 09:16) собран из `retoc_cli` -
проверено поиском путей отладочной информации в самом бинаре
(`retoc_cli\src\main.rs` встречается 3 раза, `retoc\src\main.rs` - 0).
Так что фикс в нём есть. Но полагаться на это нельзя.

**Лечится удалением `retoc/src/main.rs`** - файл ничем не используется,
бинарь собирается из `retoc_cli`. Не сделано на момент этой записи:
согласовывается отдельно, чтобы не смешивать с проверкой фикса.
