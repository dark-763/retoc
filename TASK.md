# Контекст задачи

Форк retoc с девятью правками для пересборки контейнеров IoStore UE 4.26.
Рабочая ветка ue426-repack - не трогать. Экспериментировать в bundle-rule.
Ветка pack-raw-compression - для открытого PR, не трогать.

## Задача

Правка 7 (разбивка бандлов) - костыль: разбивка читается из JSON, снятого
с оригинального контейнера, через RETOC_BUNDLE_LAYOUT. Научить retoc
вычислять её самому.

## Что уже выяснено (проверено на 1243 пакетах, 0 расхождений)

Число бандлов = максимальный целевой бандл во внешних дугах графа + 1.

Регион графа (graph_off, graph_size):
  uint32 число импортируемых пакетов
    на пакет: uint64 FPackageId, uint32 число дуг, пары (uint32 from, uint32 to)
Поле to - номер принимающего бандла. to==1 бывает тогда и только тогда,
когда бандлов больше одного (557 однобандловых - ни разу).

retoc УЖЕ строит эти дуги верно: у пересобранного пакета граф совпадает
с оригиналом, включая целевой индекс 1. Данные есть, не используются.

Бандлы содержат команды (экспорт, Create|Serialize), а не экспорты:
сумма записей = export_count * 2.

Осталось распределение команд. На 1215 пакетах: у 1125 ровно один экспорт
имеет Create в бандле 0 и Serialize в бандле 1 - родитель сериализуется
после своих детей. У 394 из 487 проверенных такой экспорт имеет потомков
(другие экспорты ссылаются на него как outer).

## Статус (ветка bundle-rule)

`compute_bundle_layout()` в zen_asset_conversion.rs вычисляет разбивку из
`export_load_order` (последовательность Create/Serialize, которую retoc и
так строит верно - сверено побайтово с оригиналом на всех 1243 пакетах
через `to-legacy` -> `to-zen` без JSON).

Правило: разрез сразу после Serialize, если следующая по порядку команда -
это **Create** экспорта с МЕНЬШИМ индексом ("инверсия" - кукер отложил
создание чего-то раньше стоящего в файле до готовности чего-то более
позднего, признак настоящей перекрёстной зависимости между ветками дерева).

RETOC_BUNDLE_LAYOUT оставлен как необязательное переопределение поверх
вычисленного правила (`json_bundle_layout_override`): если переменная не
задана - работаем полностью на расчёте; если задана и в JSON есть запись
для пакета - берём её вместо расчёта. Так старый эталонный JSON остаётся
рабочим резервным путём для пакетов, на которых расчёт ошибается.

**Важно, была найдена и исправлена ошибка до коммита.** Первая версия
правила допускала разрез и когда следующая команда - Serialize (не только
Create) с меньшим индексом; это давало 1208/1243 (97.2%) точных совпадений
на ИЗВЕСТНОМ множестве из 1243 многобандловых пакетов, но при сборке ВСЕГО
проекта (17095 пакетов, `to-legacy` -> `to-zen` без JSON на всём
`D:\GameLoc-new\original_backup`, не на подмножестве) обнаружила 131 ложное
срабатывание на пакетах, у которых в оригинале ровно один бандл (например
BP_TunnelBend_90: было 1, стало 2) - тест на одном лишь известном
множестве 1243 пакетов не мог поймать такую регрессию, потому что оно по
построению (dump_bundle_layout.py) содержит только уже-многобандловые
пакеты. Правило сужено до "только Create" - на всём проекте (17095 пакетов)
это даёт **0 ложных срабатываний** ценой меньшей полноты: 1134/1243 (91.3%)
точных совпадений вместо 1208, разница полностью в сторону "бандлов
меньше, чем в оригинале", никогда не больше.

## Дедупликация дуг (правка №8, вторая итерация)

### Что означает поле `from`

Гипотеза из постановки задачи (0=Create, 1=Serialize, 2=пакет готов целиком)
**отвергнута**. Прямая проверка по данным оригинала (все 17095 пакетов,
103073 дуги, читал `D:\GameLoc-new\raw_out_0916\chunks\<cid>` напрямую с
диска - `unpack-raw` уже распаковал оригинал туда, не нужно гонять `retoc
get` по одному чанку): для КАЖДОЙ дуги проверил `from < export_bundle_count
пакета-источника` (просмотрел исходный пакет по `pkg_id` из дуги) - **выполняется
всегда, без единого исключения** (103071 из 103071 проверенных; 2 дуги
сослались на пакет вне манифеста, видимо движковый). Будь `from` типом
команды, а не индексом бандла, он бы никак не был ограничен числом бандлов
СОВЕРШЕННО ДРУГОГО, произвольного пакета - совпадение было бы случайным.
Значит **`from` - это в точности то, что и предполагает текущий код
(`from_export_bundle_index`): индекс бандла экспортов В ПАКЕТЕ-ИСТОЧНИКЕ**,
из которого что-то нужно этому пакету раньше, чем бандл `to` в НЁМ САМОМ
станет готов к использованию.

Распределение `from`: 0 (101295), 2 (1478), 1 (298), 0xFFFFFFFF=-1 (2,
служебное значение "источник не найден", см. `fixup_legacy_external_arcs`).
Наблюдение из постановки "2 только в паре с to==1" почти верно, но не
абсолютно: пар (2,1) - 1444, но есть и (2,2) - 34 штуки. Не противоречит
интерпретации "from - это индекс бандла": `from=2` просто требует, чтобы у
ПАКЕТА-ИСТОЧНИКА было хотя бы 3 бандла, что редко (отсюда и редкость from=2
вообще), а to может быть любым бандлом ЭТОГО пакета, куда бы ни попала
конкретная зависимость.

### Настоящая причина 0 из 1134

Правка №8 убрала `from_export_bundle_index` из ключа дедупликации ПОТОМУ
ЧТО на момент создания дуги это ещё не настоящий индекс бандла, а
одноразовый номер-заглушка (`legacy_external_arc_counter`, инкрементируется
на КАЖДЫЙ вызов) для последующей подстановки в `fixup_legacy_external_arcs`
- дедуп по нему был бессмысленным (каждая дуга уникальна по построению) и
только размножал дуги. Но ключ без `from` тоже неверен: оригинал хранит и
`(id, from=0, to=1)`, и `(id, from=2, to=1)` - то есть `from` ПОСЛЕ
разрешения значим и дедуп обязан его учитывать.

Ловушка в том, что "правильный from" вычисляется ТОЛЬКО в отдельном
глобальном проходе `fixup_legacy_external_arcs`, который выполняется ПОСЛЕ
того, как ВСЕ пакеты уже сериализованы в байты (см. вызов в
`retoc_cli/src/main.rs` ~927: сначала все `build_zen_asset` в `converted_lookup`,
потом цикл `fixup_legacy_external_arcs` по каждому, потом запись на диск) -
именно потому, что зависимость может указывать на пакет, который ещё не
обработан (`rayon`, порядок не гарантирован). До этого прохода МЫ НЕ ЗНАЕМ,
разрешатся ли два разных импорта одного и того же внешнего пакета в один и
тот же бандл или в разные - поэтому дедуп в момент создания дуги (что
правка №8, что первая попытка её поправить в этой сессии - ключ по
`package_object_import`) в принципе не может быть точным: первый вариант
схлопывает то, что не должно схлопываться (испытано и отклонено выше),
второй наоборот пропускает дубли (проверено: пакет `12902175980756718967`
получал 17 одинаковых `(0, 1)` дуг вместо одной - 17 разных импортов ИЗ
этого пакета оказались все в его бандле 0).

**Правильное место для дедупликации - ПОСЛЕ `fixup_legacy_external_arcs`**,
когда `from` уже настоящий. К этому моменту пакет уже полностью
сериализован в байты (`self.package_buffer`), а не хранится как структура -
переделывать архитектуру (откладывать сериализацию до глобальной фиксации)
не стал: это большая, рискованная переделка ради узкой задачи. Вместо этого
`dedup_legacy_dependency_arcs()` в `zen_asset_conversion.rs` патчит уже
сериализованные байты НАПРЯМУЮ:

1. Область графа - всегда последняя часть заголовка для
   `container_header_version <= Initial` (проверено по `FZenPackageHeader::serialize`
   - `header_size` фиксируется сразу после записи графа), поэтому её можно
   сжать, просто вырезав лишние байты (`Vec::splice`) - ничего до неё или
   после нужного пересчёта смещений не требует (данные экспортов идут
   отдельным куском сразу после и просто сдвигаются как единый блок).
2. `graph_data_size` лежит по фиксированному смещению 56 байт от начала
   `FZenPackageSummary` для `<= Initial` (проверено побайтово: 8 байт name +
   8 байт source_name + 4 package_flags + 4 cooked_header_size + 4×4 полей
   name map + import_map_offset(4) + export_map_offset(4) +
   export_bundle_entries_offset(4) + graph_data_offset(4) = 56) - патчится
   тем же способом, каким код уже патчит отдельные `from` в этом же файле.
3. `store_entry.export_bundles_size` (= header_size + сумма размеров
   экспортов) уменьшается на столько же байт, на сколько сжался граф.
4. Дедуп идёт ПОБЛОЧНО (в пределах одного импортируемого пакета), парой
   `(from, to)`, с сохранением порядка первого вхождения.

### Проверенные и отвергнутые гипотезы (не тратить время повторно)

- Настоящий флаг EObjectFlags::Public у экспорта - не коррелирует с границей
  (только 49 из 1271 реальных границ на экспорте с этим флагом).
- Любой экспорт с детьми (Outer) как триггер границы - даёт тысячи ложных
  срабатываний на больших/глубоких пакетах.
- "Корневой" (Outer==NULL) экспорт с детьми - предсказывает не тот узел на
  глубоко вложенных пакетах (граница может быть на внуке корня, не на корне).
- Цель preload-зависимости SerializeBeforeCreate (данные для этого УЖЕ
  корректно вычисляются и используются для порядка, см. export_dependencies)
  - слишком широкий сигнал, совпадает почти с каждым Serialize в пакете.
  Настоящие межпакетные циклы (прямой 2-цикл через imported_packages) тоже
  проверены на SQ_Barghest2 - не найдены, разбивка похоже чисто внутрипакетная.
- Обнуление глубины вложенности (открытые Create без Serialize) - см. выше.
- "Чистый остров" (span Create..Serialize контейнера содержит только его же
  потомков, без посторонних) - даёт тысячи ложных срабатываний, т.к. в
  глубоких деревьях таких чистых островков много на разных уровнях, а
  реальная граница - только на одном конкретном.

Для отладки полезны написанные в этой сессии python-скрипты (запуск через
`to-legacy` в D:\retoc\target\release\retoc.exe --version UE4_26` на
`D:\GameLoc-new\original_backup`, затем `--override-container-header-version
Initial to-zen`) - см. историю сессии, в частности dump_one.py (печатает
Outer/class/позиции конкретного пакета) и verify_final2.py (сверка целого
пересобранного контейнера с bundle_layout.json).

## imported_packages (правка №10, ветка imported-order)

Нумерация: компрессия в pack-raw уже занимает №9 в README-ue426.md/
PATCHES-en.md (была реализована раньше, в ветке ue426-repack) - эта правка
десятая по счёту, не девятая (в первом коммите на этой ветке ошибочно
назвал её "fix 9", в документации и далее в TASK.md - "fix 10").

### Задача

`StoreEntry.imported_packages` не совпадал на 3625 из 17095 пакетов. В
TASK.md/PATCHES-en.md (fix 5) это числилось как "отличается только порядок,
кукер не сортирует этот список" - но это никогда не проверялось предметно.

### Состав vs порядок

Из 3625 расхождений у **3618 состав идентичен** (тот же набор ID, другой
порядок), у **7 состав расходится** - и это ВСЕГДА одна и та же картина:
у оригинала на один элемент больше, у нас его вообще нет.

Проверено на всех 17095 пакетах (`to-zen` без RETOC_BUNDLE_LAYOUT из
`D:\GameLoc-new\fin_0916`, сравнение с `D:\GameLoc-new\raw_out_0916`).
7 "лишних в оригинале" ID (`10302301616881458927` встречается в 6 пакетах,
`7979332950583999727` в одном - PERSISTENT.umap) не соответствуют НИ ОДНОМУ
cid ни в нашем манифесте, ни в оригинальном - то есть это ссылка на пакет, у
которого попросту нет собственного чанка в этом контейнере (внешняя/чужая
зависимость, а не движковый ассет и не что-то из известных пробелов).

Причина найдена в `resolve_package_import_internal_legacy` (`asset_conversion.rs`,
направление zen -> legacy): для `container_header_version <= Initial`
разрешение импорта идёт НЕ по индексу в `imported_packages`, а поиском - код
перебирает ВСЕ пакеты из `package_header.imported_packages` оригинала и ищет
среди их экспортов совпадение по `legacy_global_import_index()`. Значит
`imported_packages` в оригинале - самостоятельный список, не обязанный 1:1
соответствовать `import_map` пакета: кукер мог занести туда пакет, на который
есть зависимость, но НИ ОДИН элемент `import_map` на него не ссылается
напрямую (что-то вроде "мягкой"/учётной зависимости без прямого импорта
объекта). У таких 7 пакетов `to-legacy` не создаёт для этой зависимости
никакой записи в таблице импортов легаси-файла вообще - ни обычной, ни
"голого пакета" - потому что реконструировать её неоткуда: в `import_map`
исходного zen-пакета для неё просто нет соответствующей записи. Проверено
экспериментально: добавление в `to-zen` кода, который дополнительно
регистрирует "голые" (без вложенного объекта) пакетные импорты в
`imported_packages`, не изменило результат ни на одном из 7 пакетов - значит
потеря происходит раньше, при `to-legacy`, не при `to-zen` (правка отменена,
в текущем коде её нет). Чинить пришлось бы синтезом лишней записи импорта
прямо в `to-legacy` по данным `imported_packages` контейнера-источника - это
трогает другой файл и другое направление конвертации ради 7 пакетов из
17095 (0.04%), решено не делать в рамках этой задачи.

### Порядок: перебор гипотез

Проверено на оригинальном манифесте (`D:\GameLoc-new\raw_out_0916`), без
пересборки, по всем 7337 пакетам с >1 импортом:

| гипотеза | точных совпадений |
|---|---|
| по `FPackageId` (возр./убыв.) | 18.0% / 10.0% |
| по глобальному `load_order` импортируемого пакета (возр./убыв.) | 7.9% / 21.0% |
| по длине пути | 22.2% |
| по basename (без пути) | 36.8% |
| **по имени пакета (`/Game/...`), регистронезависимо, по алфавиту** | **98.6%** |

Алфавитный порядок по имени пакета (не по диречному пути - тот дал 98.61%,
имя `/Game/...` чуть точнее, 98.66%, вероятно потому что это тот же формат
строки, который использует сам кукер) на порядок точнее всех остальных
гипотез. Реализовано в `zen_asset_conversion.rs`,
`build_zen_dependency_bundles_legacy`: `imported_package_names` теперь
заполняется и для legacy (<= Initial) пути импорта (раньше заполнялся
только для UE5.0+), после чего `imported_packages` /
`imported_package_names` / `external_package_dependencies` переупорядочиваются
одним стабильным `sort_by` по `to_lowercase()` этого имени. Безопасно: обе
арки (external/legacy dependency arcs) адресуются по ID пакета или по паре
(исходный пакет, индекс импорта), не по позиции в этих трёх массивах, а
блоки графа сортируются отдельно по `FPackageId` уже на сериализации
(`zen.rs`, `non_empty_dependencies.sort_by_key`) - переупорядочивание не
могло задеть ни то, ни другое, что и подтверждено измерением (см. ниже).

Проверенная и отвергнутая гипотеза: "порядок первого обращения при обходе
экспортов 0..N, Create-зависимости потом Serialize-зависимости" (тот же
проход, что строит `legacy_dependency_arcs` в `build_zen_dependency_bundles_legacy`)
- дала РЕЗУЛЬТАТ ХУЖЕ исходного (5936 расхождений вместо 3625) и была
отброшена, а не просто не помогла.

### Результат

На всех 17095 пакетах (`to-zen` без JSON): расхождений `imported_packages`
стало **93** (86 порядок + те же 7 состава) вместо 3625 - точных совпадений
99.46% вместо 78.8%. `export_count`, `export_bundle_count` (109, как и было),
`export_bundles_size` (2559, ожидаемо от перевода) не изменились. Побайтовое
совпадение области графа (та же проверка, что и в разделе про дедупликацию
дуг) осталось ровно 15856/17095 (92.75%) - переупорядочивание не затронуло
арки, как и предполагалось по устройству кода.

### Остаток (86 расхождений порядка)

Не однородны:
- **55 из 86** объясняются одним правилом: оригинал выносит РОВНО ОДИН пакет
  в начало списка (перед алфавитным порядком остальных). Во всех
  просмотренных случаях этот "вынесенный" пакет выглядит как класс-родитель
  Blueprint'а или похожая на него системная зависимость (например

  импорт с индексом 0", но точно не проверялось (потребовался бы разбор

- **31 из 86** сложнее: внутри списка держатся вместе плотные "кластеры"

Проверка от пользователя: `patch_smart.py` подменяет `StoreEntry` только у

`WBP_RightPanel...` ЕСТЬ в `patch_0916.txt`, и `patch_smart.py` корректно
подставляет туда НАШИ данные (7 элементов, без фантома, порядок

Реальная причина - глубже и никак не связана с патч-листом. Минимальный
воспроизводимый опыт (без сжатия, чтобы исключить компрессию как фактор):
взял чистую распаковку оригинала, пропатчил `patch_smart.py`, проверил
manifest.json ДО `pack-raw` (7 элементов, порядок наш) - прогнал

`10302301616881458927`) в ДРУГОМ порядке. Дальше сравнил ВЕСЬ манифест
до/после этого же pack-raw (один прогон, не сравнение двух сборок):
**85 пакетов из 17095 меняют порядок `imported_packages`** между "что мы
записали в manifest.json" и "что вернул `pack-raw` -> `unpack-raw`", один
из них (тот самый `WBP_RightPanel`) вдобавок получает лишний элемент.

Это самостоятельный, ранее не описанный баг в `pack-raw`/`unpack-raw`
(`retoc/src/container_header.rs`), не зависящий от сжатия, от того, что мы
передаём на вход (проверено на данных ОБЕИХ веток - `ue426-repack` без
сортировки и `imported-order` с сортировкой дают ПОСЛЕ pack-raw ОДИНАКОВЫЙ
результат для одних и тех же 85+1 пакетов). `git log` подтверждает:
`container_header.rs` не менялся НИ В ОДНОМ нашем коммите (fix 1-10) - баг
целиком в неизменном апстримном коде, я его туда не вносил. Механизм
(почему именно эти 85, почему именно такой порядок) не нашёл - грепал
`container_header.rs` вдоль и поперёк (`ser_no_length`, `ser_array`,
offset/count структура `TFilePackageStoreEntryCArrayView`) и не увидел ни
одного явного `.sort()` или похожего преобразования; дальше не копал,
входит не в объём этой задачи. **Возможно (не проверено), что эти же 85
объясняют часть "необъяснённых 86" из investigation fix10** - если
`D:\GameLoc-new\raw_out_0916` (эталон, с которым все сравнения велись) сам
был снят через `pack-raw`, а не прямой распаковкой оригинала, для
патчащихся файлов он может отражать этот же артефакт, а не то, что
реально лежит в `original_backup` - есть прямое расхождение между
`raw_out_0916` и свежей распаковкой `original_backup` именно для
`WBP_RightPanel` (другой порядок ДО всякого pack-raw с нашей стороны) -
недообследовано, увидел по дороге, для другой задачи.

**Практический вывод (ради которого всё это проверялось): на РЕАЛЬНУЮ,
установленную в игру сборку сортировка `imported_packages` эффекта не
имеет вообще** - `pack-raw` переписывает порядок независимо от того, что
ей передали. Правка №10 полезна только при прямом сравнении дампов
(`to-zen` -> `unpack-raw`, без `pack-raw`) - например при сверке с
`bundle_layout.json`-подобными эталонами. Для нашего реального перевода
(через `patch_smart.py` + `pack-raw`) её можно не переносить в
`ue426-repack` - результат будет тот же самый, что и без неё. Для чужих
форков/сценариев без такой подмены чанков сортировка всё ещё может быть
полезна как более точное соответствие оригиналу на уровне прямого dump'а.

### Подозреваемый 3 (расчёт бандлов, fix 7) - текущий фаворит

Рабочая (до сегодняшнего дня) резервная сборка датирована 16 сентября -
раньше и коммита с расчётом бандлов (`2c52201`), и коммита с починкой
таймингa дедупа арок (`6500ba2`, 17 сентября 15:59). Похоже, она собрана
с `RETOC_BUNDLE_LAYOUT` (JSON), а не расчётной раскладкой. Обе сборки,
собранные и сравненные выше (`ue426-repack`, `imported-order`), шли БЕЗ
JSON - то есть обе несут одни и те же 109 пакетов с неверным числом
бандлов и 1239 неверных дуг (см. раздел про дедупликацию дуг выше).

В `AsyncLoading2.cpp` (UE 5.0) зависимости между export-бандлами
реализованы через барьеры (`FEventLoadNode2::AddBarrier`/`DependsOn`/
`ReleaseBarrier`) - узел не начинает выполняться, пока не сняты ВСЕ его
барьеры. Дуга с `to_export_bundle_index`, указывающим на бандл, которого у
целевого пакета физически нет (наш расчёт дал бандлов МЕНЬШЕ, чем в
оригинале - единственное направление ошибки по fix 7), в этой модели не
обязана крэшить - она может создать барьер, который никогда не будет снят
(зависимость на несуществующий/недостижимый узел), что даёт ровно
"тихое зависание без лога и окна", как было описано. Оговорка: в этом
файле (5.0) НЕТ ветки для legacy/Initial-формата дуг вообще (только
новый, по хешу импорта) - 4.26 грузил как-то иначе, точный код недоступен,
это архитектурная аналогия, не доказательство для конкретно нашего
формата.

**Следующий шаг**: собрать третий вариант - тот же код (расчёт бандлов +
починка дедупа арок + сортировка `imported_packages`, раз она теперь
подтверждённо безвредна и бессмысленна для реальной сборки), но С
`RETOC_BUNDLE_LAYOUT` (гибридный путь: JSON есть - берём из него, иначе -
расчёт). Заодно - прямая проверка механизма: среди 10 из 109 "плохих"
пакетов, что реально патчатся (см. раздел про imported_packages,
"Проверка 3"), проверить в БЕЗ-JSON сборке, есть ли дуги с
`to_export_bundle_index`, которого не существует у целевого пакета - если
да, механизм зависания подтверждён напрямую по данным, а не только по
